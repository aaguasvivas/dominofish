The brief is docs/prompts/BUILD.md; this file holds the plan refined from it, the decisions with reasons, and the owner's answers word for word. Feature entries and their verify commands are in docs/features.json; progress is in docs/progress.md.

## Architecture and API

Cargo workspace (decision D1):
- crates/dominofish-core, library: rules, information sets, sampling, search. No I/O, global state, threads, or clocks; no dependencies; builds for wasm32-unknown-unknown at every commit (check.sh).
- crates/dominofish, binary dominofish: the command line (selfplay, engine, match, bench, solve-stats, bench-positions, report, capi-fuzz, and playout-bench now; analyze and review later) and all process and file I/O.
- crates/dominofish-wasm, cdylib (since M1-10): extern "C" exports with no wasm-bindgen: playouts_checksum for the native and wasm checksum (M1-10), and board_alloc, board_request, and board_free, the text request interface of the web board (M11-01, docs/FORMATS.md, Board requests).
- web/, the web board (M11-01, owner decision 8): plain HTML, CSS, and JavaScript with no dependencies, built by scripts/build-web.sh into one self-contained page, web/dist/index.html (gitignored), with the wasm module inline and run in a Web Worker.
- Planned: a native crate that splits one call's worlds across threads and merges them to the one-thread result (hard constraint 1), when search exists.

Core state (M0, rules.rs): per-seat hand masks (u32, 28 bits in Capi's tile order), a board mask with left and right ends, the 1v1 boneyard as an ordered array popped from its end, turn, opener (starterThisRound), last player, one pass counter, scores, target, phase, and the next round's leader. The automatic round-1 tile and the opener tie-breaks follow reducer.ts:90-185 and need the deal's hand order, which the Deal type keeps.

Moves (provisional until docs/RULES.md at M1-01, decision D6): Play { tile, end }, Draw, Pass. On an empty board `end` selects the orientation (Left: as dealt, low pip left; Right: flipped). The canonical generator emits one move per tile on an empty board (as dealt), one per tile and fitting end otherwise, and only the left end when both ends show the same pip. Events are typed (Domino, Capicua, Tranque, PaseCorrido, PaseSalida) and map to Capi's callouts only in the parity harness.

Hot-path bounds (the research digest, docs/research/2026-10-25-prior-art.md, section 1.8; "digest" below means that file): at most 12 distinct plays (MoveList holds 16); a 1v1 hand holds at most 21 tiles; a round has at most 128 plies; the boneyard holds at most 14 tiles. Hot-path buffers are fixed-size arrays sized from these bounds.

Public API (M2 on; hard constraint 1; the InfoSet exists since M2-01, D10; Limits and analyze are planned for M4): InfoSet built from a game record and a seat (own hand, public history, hand sizes, boneyard count, scores, target, opener, derived voids, 1v1 opening deductions); Limits (worlds, nodes, memory cap); analyze(&InfoSet, &Limits, seed) -> Analysis (each legal move's value, the chosen move, information-set size, nodes). Full states stay in the referee, the simulator inside sampled worlds, and the omniscient bot.

## Method decisions

- D1, 2026-10-25. Two crates, core and command line. Reason: the no-I/O, no-clock, and wasm32 rules bind the core only; keeping every I/O dependency in the binary leaves the core with none. More crates join only when a milestone needs one.
- D2, 2026-10-25. Seeded randomness is SplitMix64 with Lemire's exact bounded integers, written in core/src/rng.rs. Reason: recorded seeds (fixtures, pre-registered runs) must keep their streams forever, and a crate upgrade could change a stream or its range reduction (rand changed its range sampling between 0.8 and 0.9). Checked: rand_core and rand_pcg would add a dependency and still need our own range reduction for stability.
- D3, 2026-10-25. The command line parses arguments with lexopt (see Dependencies). Checked: clap with derive pulls a proc-macro dependency tree and more build time for a few flags.
- D4, 2026-10-25. Property tests (M1-08) run over states reached by seeded random playouts, written as plain tests, not proptest. Reason: all randomness comes from explicit seeds (hard constraint 7) and a failing case is reproduced by its seed; shrinking a playout-generated state adds little; proptest would be a large dev-dependency tree.
- D5, 2026-10-25. Exit features use id M<k>-99 so that features appended when a milestone starts sort before its exit.
- D6, 2026-10-25. Canonical moves as stated under Architecture; final definition and the map from Capi intents in docs/RULES.md (M1-01).
- D7, 2026-10-25. Selfplay and matches deal with DominoFish's RNG; parity tests inject Capi's deals (hard constraint 2). A deal keeps hand order and boneyard order.
- D8, 2026-10-25. The tranque test is O(1): locked if and only if no tile outside the board shows either end (ALL & !board & (SUIT[L] | SUIT[R]) == 0). It equals Capi's isBoardLocked (validate.ts:45-51) because every tile is on the board, in a hand, or in the boneyard. The tranque geometry property (digest 1.4) is tested at M1-08.

- D9, 2026-10-25. The differential fuzzer (M1-07) runs Capi in Node as the driver and Rust as the verifier: fuzz.mjs streams Capi's canonical legal set before each move and a 32-bit digest of the canonical state and event after it, and `dominofish capi-fuzz` replays and compares. Reason: one stream per run instead of a round trip per move; Node is the bottleneck (about 3 minutes per 1,000,000 rounds). A digest collision could hide one mismatch with probability 2^-32 per differing move; a mismatch that diverges the state also changes the following moves' sets and digests. Fuzz seed 1 for the full and the fast run (the fast run is the first 10,000 rounds of the same stream).

- D10, 2026-10-25. The InfoSet (M2-01, core/src/infoset.rs) is built from a GameRecord (core/src/record.rs: each round's deal and moves) and a seat by replaying to the point, and keeps only public facts and the seat's own hand: board and ends, turn, opener, last player, passes, scores, hand sizes, boneyard count, round 1's automatic tile, the round's public history (each move with the ends before it; draws as counts), current-hand voids, and the 1v1 round-1 exclusions of each dealt hand (opener rule R4). 1v1 voids are time-stamped: a draw's void binds the tiles held at the draw and its non-fitting tiles, and applies to the whole hand only after the drawer's next move (the drawn tile that fits is played then); older draws bind only older tiles, which the history keeps for the world counter (M2-03). The record holds hidden tiles; only the referee and record tools read it. Reason: one replay path for every consumer, and an equality test (records that differ only in hidden tiles give equal InfoSets) checks the no-hidden-tile rule of hard constraint 1.

- D11, 2026-10-25. Consistent worlds (M2-03, core/src/worlds.rs). A world is an assignment of the tiles the seat cannot place to holder groups of fixed sizes, each tile only where it may be. 2v2: the three other hands; a tile may be in a hand unless it shows one of that seat's void pips. 1v1: the other seat's acquisition batches (its dealt hand, then the non-fitting tiles of each of its draws) and the boneyard; the tiles are the hidden ones plus the other seat's played tiles (their batch is hidden), with each draw's fitting tile pinned (it is the play right after the draw, R15); a tile may be in a batch when it avoids the ends of every draw and pass of that seat while the batch held it, and the dealt batch also avoids the round-1 exclusions. Every assignment stands for the same number of full deal orders, so the count is proportional to the number of consistent deals. The count is a dynamic program over tiles keyed by the remaining group sizes. Evidence: the counts of the Leads, the 4-6 example, the true world allowed at 9,873 decisions, and equality with a brute-force oracle that builds every candidate deal and replays the record (150 positions per mode, 133 of the 1v1 ones after a draw of the other seat). Known limit for sampling (M4): when the other 1v1 seat opened round 1 with no double, its hand order chose the automatic tile among equal pip sums, so a world where it also holds another tile of that sum stands for fewer deal orders (1/m of them for m such tiles); the count does not weight this. The counter returns None while the other 1v1 seat's draw is unresolved; a seat's own decisions never fall there.

- D12, 2026-10-25. Baseline bots (M2-04, core/src/bots.rs), each deciding from its seat's InfoSet with ties broken by its RNG: random (uniform over canonical legal moves); heaviest, bota gorda (most pips); accompanied, la mas acompanada (the exposed pip is one it keeps the most tiles of, then pips; digest 3.5 and Moreno-Montiel 2020 name it the best simple heuristic); rule (scores ends the next seat is void in, avoids ends the partner is void in, counts its own and the unseen tiles that can follow, then pips). The in-process referee (referee::play_bots) builds each seat's InfoSet from the record so far and keys each seat's RNG by the round's deal seed and the seat, so a duplicate pair of identical bots replays the same choices (M2-08). These are fixed baselines; their strength is measured only by the harness (M2-06 to M2-09).

- D13, 2026-10-25. The match harness (M2-06, crates/dominofish/src/harness.rs and engine.rs). Every seat is a separate engine process over the line protocol, so 2v2 partners share nothing; the referee sends each engine the InfoSet it builds for that seat before each go. Binaries come from scripts/build-bin.sh (git archive of the commit, built in target/old, copied to runs/bin/<commit>/); the harness refuses target/. A duplicate pair plays one deal seed twice with the sides swapping seats, deals derived per round from the seed so full games share them, and seat seeds keyed by pair and seat, which makes identical deterministic bots score exactly 0 per pair. Amended 2026-10-25 after the M2 review: seat seeds come from a separate engine seed base (`match --engine-seed`, required), derive(derive(base, pair), 100 + seat); the header sent to engines holds no seed and carries the budgets, threads, and tables each side's engines report in their ready line; the deal seeds and the engine seed base go only to the results file. Before this, the header held the deal seeds and the seat seed was derive(deal seed, 100 + seat), which an engine could invert to rebuild every hidden tile. Each reply has one deadline, and a line other than info that waits before a go is a protocol fault. A per-reply deadline (--timeout-ms, default 10 s) is a safety limit; budgets are nodes or worlds (hard constraint 7). Binary identity uses FNV-1a 64 of the file, written here instead of adding a hash crate because it is an identity check, not a security one.

- D14, 2026-10-25. The SPRT (M2-07, crates/dominofish/src/stats.rs) is a normal-approximation GSPRT on per-pair results with the sample variance (after the Fishtest normalized GSPRT idea, digest 2.3), alpha = beta = 0.05, Wald bounds, and no decision before 16 pairs; `dominofish match --sprt mu0,mu1` runs it on the pair margin in points and stops at a decision. Confidence intervals are normal 95% intervals over pairs: points per round (pair margin over its rounds) and game-win rate (pair wins over 2). T1 checks the error rates on synthetic data. Game-win SPRTs (M6) and Elo are not used in M2. Amended 2026-10-26 after the M3 review: points per round use a t interval over pairs (exact quantiles up to 6 degrees of freedom, then the Cornish-Fisher expansion, within 0.001), and the game-win rate uses a Wilson score interval over the 2n games of n pairs, because a normal interval over pairs collapses to [1.000, 1.000] when one side wins every game; the Wilson interval treats the games as independent, which is conservative here, since the two games of a pair share a deal. The SPRT is unchanged. REPORT.md recomputes every run's intervals this way; the README rows moved by at most 0.03 points (R2) and widened for R3's 16-pair rows.

- D15, 2026-10-25. The exact solver (M3-01, core/src/solver.rs). Its value is the rest of the round's margin, team 0 minus team 1 (bonuses paid from here on plus the round's points), under perfect play by every seat; team 0's seats maximize and team 1's minimize. Fail-soft alpha-beta with a transposition table of 2^bits entries of 16 bytes, always replaced, each holding the full 64-bit key, a value, a bound (exact, lower, upper), and the best move; table bounds only cut off and never narrow the window, so every stored bound is one its searched window proves, and the root never returns from the table. Key: State::position_hash (every tile's place, the ends, turn, opener, last player, passes, and the boneyard position) plus, per team, the bonuses it can still receive this round, (target - 1 - score) / 25 in 2v2 and 0 in 1v1: the value depends on the scores only through the cap R25, so positions that differ only in scores with equal counts share entries. A table serves one deal, because the 1v1 boneyard order is not hashed; Table::clear starts a new deal. Move ordering: the table's move, then plays by 2 x pips + 3 for a double (digest 2.2, the DDS ideas). Node cap: 10,000,000 nodes per solve by default (the 1v1 heavy tail, digest 2.2); past it the solver picks, among the root's legal moves, the one whose points plus a greedy playout after it (every seat playing the first move of that ordering) are best for the mover, and returns that value; the search's partial results are discarded. The search allocates nothing (M1-09's test counts solver nodes and capped solves). Evidence: docs/features.json M3-01. Bench (M3-02): fixtures/bench.txt holds 16 full-round positions per mode from `dominofish bench-positions --games 8 --seed 2026`, solved at the default cap and a 2^20-entry table on one thread; check.sh runs it twice and compares.

- D16, 2026-10-25. The omniscient bot (M3-04, crates/dominofish/src/engine.rs). `dominofish engine --bot omniscient` says view=omniscient in its ready line; the referee then also sends it the full state before each go (docs/FORMATS.md, Engine protocol), and it plays the exact solver's move (D15) with the default node cap and table, cleared at each round. The header records its view, budgets (nodes:<cap>), table size, and Bench (the harness runs `<binary> bench`, whose positions are built into the binary); the report marks it "(cheating)". It is the upper bound for comparison, never a goal, and never a bot that plays fairly; every other engine still receives only its InfoSet, which M3-04's spy check confirms.

- D17, 2026-10-26. The world sampler (M4-01, core/src/sampler.rs). It draws one consistent world at a time, in proportion to the number of consistent deals the world stands for. From the M2-03 groups and allowed masks (D11), a dynamic program over the tiles in a fixed order counts, for each tile and each vector of remaining group sizes, the completions of the later tiles; a world assigns each tile in turn to an allowed group with probability proportional to the completions left after that choice, using Lemire's exact bounded integers over 64-bit counts. Every step keeps a completion, so the sampler never backtracks and has no fallback; a zero total is an error, counted as a fallback (it must read 0), and the sampler sees only the InfoSet, never the true hands. 2v2: an assignment is the three other hands. 1v1: the other seat's hand is its batch tiles not yet played, and the boneyard order is a uniform shuffle of the boneyard group (draws pop from the end). After a round-1 opening of the other 1v1 seat with no double, a world whose dealt batch holds m tiles of the opening tile's pip sum stands for 1/m of the deal orders (D11, known limit), so the sampler accepts it with probability 1/m and otherwise draws again. A world's State comes from the InfoSet's public fields with the sampled hands and boneyard (State::from_parts). Evidence: T3.
- D18, 2026-10-26. PIMC (M4-02, core/src/pimc.rs). analyze(&InfoSet, &Limits, seed) draws Limits.worlds worlds with the D17 sampler from an RNG seeded with seed and, in each world, solves every legal move exactly: the move's points plus the solver's value of the state after it (D15), with a node cap per solve and a table of 2^16 entries (1 MB) cleared per world. The table size comes from the 2026-10-26 profile (docs/eval/results/2026-10-26-solver-profile.md): 2^16 entries solved the same positions 1.9 times faster than 2^20 in 2v2 and 1.6 times faster in 1v1, because a 16 MB table misses the cache; Bench, solve-stats, and the omniscient bot keep 2^20. The same worlds serve every move. A move's value in a world is from the seat's team view (team 0's margin, negated for team 1); moves are ranked by their mean over worlds, with the standard error over worlds, and the chosen move has the highest sum, ties to the generator's order. A capped solve takes the solver's greedy value (D15) and is counted. The Analysis reports each move's mean and standard error, the chosen move, the information-set size (the exact count of M2-03), worlds, nodes, capped solves, and the sampler's inconsistency and fallback counts. The engine (`engine --bot pimc`, M4-03) plays a forced move without search and seeds each other decision with the next value of its round RNG (the bots' scheme, D12). Known limits (Leads, algorithms[4] and [24]): inside a world every seat sees every hand, so 2v2 PIMC treats the partner as omniscient, and 1v1 PIMC treats the boneyard order as known; M8 and M9 address them. Default worlds per move (M4-07), rule stated 2026-10-26 before its runs: W is the largest of 32, 64, and 128, tried in that order and stopping at the first that fails, for which `dominofish pimc-stats --games 20 --seed 1,100,000,000 --worlds W` (the non-forced decisions of 20 dev-range selfplay games) gives a p90 time per move of at most 1,000 ms in both modes, in the slower of two runs, one thread, with commit and load recorded; if 32 fails, 16. A probe at W = 16 on 10 of these games gave a p90 of 171 ms (2v2) and 58 ms (1v1) at load 3.0. Matches with PIMC set --timeout-ms 120,000: the slowest decisions of the probe took 1.2 s (2v2) and 2.4 s (1v1) at 16 worlds, so the 10 s default safety limit would void runs at 64 worlds or more.

Every consistent world is enumerated by the replay oracle of tests/worlds.rs (every assignment by group sizes alone, kept if the rebuilt deal replays the public record, the seat's hand, and the scores), each with a weight: 1, or, after a no-double opening of the other seat, the number of the 5,040 orders of that seat's dealt tiles under which State::first_round gives the observed opener and tile. The sampler draws N = ceil(10 / p_min) worlds, p_min being the smallest world probability, with seed 7,000,000 + 1,000 c + d (c = 0 for 2v2, 1 for 1v1, 2 for no-double; d the decision's index in its set). Pearson X^2 over the enumerated worlds with df = worlds - 1; p from the regularized incomplete gamma function. Pass in each set: at most 5 of 100 decisions with p < 0.01 (P(Bin(100, 0.01) >= 6) = 0.0005), and at most 2 of 30 in the no-double set (P(Bin(30, 0.01) >= 3) = 0.0033); and the pooled X^2 of the set has p >= 0.001 against the summed df. (b) The true world. At every decision of the 200 games per mode with a count above 1 (no-double openings excluded; set (a) covers their weights), 100 worlds with seed 7,500,000 + 1,000,000 c + d; H is the number of draws equal to the true assignment, E = the sum of 100 / count, and V = the sum of 100 (1 / count)(1 - 1 / count). Pass: |H - E| <= 3.29 sqrt(V) in each mode (two-sided 0.001), with E >= 200. (c) Consistency. Every world drawn in (a) and (b), rebuilt into a deal with the sampled boneyard order, replays the round's public record, the seat's hand, and the scores, and the sampler's State equals the replayed state; inconsistent worlds and sampler failures (fallbacks) must both number 0.

## Seed ranges

Seeds are u64. A run uses deal seeds base + i for pair i and records its base and maximum pair count here before it starts.

| Range | Use |
|---|---|
| 0 to 999,999,999 | tests, fixtures, parity, perft, benches, selfplay examples; never a strength result |
| 1,000,000,000 to 1,999,999,999 | dev deals: tuning and exploratory matches |
| 2,000,000,000 to 2,999,999,999 | held-out deals for strength claims (SPRT runs, README numbers) |
| 3,000,000,000 to 3,999,999,999 | held-out games for calibration and inference quality (M6 Brier, M8 sampling ratio); never used to build tables or train |

| 5,000,000,000 to 5,999,999,999 | engine seed bases (`match --engine-seed`), chosen apart from any deal seed and never computed from one |
